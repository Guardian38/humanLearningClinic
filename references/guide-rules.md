# 이해 가이드 작성 원칙

가이드는 강의를 다시 옮긴 것이 아니다. 강의를 옮긴 것은 `요약.md`(정의 원문, 쪽수)가 맡는다. 가이드는 개념마다 "왜 필요한지, 무엇을 하는지"를 이해시키는 설명을 그 위에 얹는다. 형식과 빌드는 `scripts/build_guide.py` 첫 주석, 예시는 `examples/guide/`를 본다.

## 1. 원본과 범위

1. **요약.md보다 앞서가지 않는다.** 정의·정리·식은 요약.md에 있는 것을 쓴다. 요약에 없는 강의 내용이 필요하면 요약.md에 먼저 넣고(근거 쪽수와 함께) 가이드에 쓴다. 정의를 인용할 때는 `<div class="def">원문 <span class="ref">[p33]</span></div>`로 요약과 같은 문장과 쪽수를 쓴다.
2. **시험 범위 안에서만 쓴다.** 범위는 1절 4번에서 사용자와 정한 것이다. 범위 밖이지만 이해에 꼭 필요한 배경은 "참고"로 표시하고 짧게 쓴다.
3. **강의 용어와 표기를 따른다.** 문제 작성 원칙(`question-rules.md` 1절 2번)과 같다. 이해를 돕는 비유를 쓸 수 있지만, 비유가 강의 용어처럼 읽히지 않게 "비유하면"이라고 밝힌다.

## 2. 단원과 절의 구성

- 단원 하나 = 본문 조각 하나(`units/<단원 키>.html`). 단원 키는 클리닉의 `units` 키와 같다.
- 절(`<h2 id>`)은 개념 하나나 밀접한 개념 몇 개를 다룬다. 개념 절에는 `data-c="<개념 id>"`를 붙인다. 개념 하나가 여러 절에 나오면 처음 나온 절이 클리닉 링크의 대상이 되므로, 그 개념의 중심 설명을 먼저 둔다.
- **절의 서술 순서**: 왜(이 개념이 없으면 무엇이 안 되나) → 직관(그림, 비유, 한 줄 요약 `.oneline`) → 식(`.formula`) → 직접 해보기(`.lab`, 넣을 때만) → 자주 하는 오해(`.pit`). 모든 절에 다섯 가지를 다 넣지 않는다. 얇은 개념은 한 줄 요약과 식이면 충분하다.
- 단원 끝에는 "스스로 점검하기" 절을 둔다(3절).
- 다른 단원과 이어지는 곳은 링크로 잇는다: `<a href="#c-2.vol">Ch.2 행렬식</a>`, `<a href="#u-3">`. 첫 화면 조각(`home`)에 "개념 연결 지도"(개념, 처음 등장, 다시 쓰이는 곳) 표를 두면 단원 사이의 흐름이 보인다.

### 상자

| 상자 | 쓰는 때 |
|---|---|
| `box idea` 핵심 | 절의 요점, 여러 조건이 같은 사실이라는 정리 |
| `box pit` 자주 하는 오해 | 흔한 실수, 헷갈리는 짝. 왜 틀렸는지까지 쓴다 |
| `def` 정의 인용 | 요약.md의 정의 원문과 쪽수 |
| `box mine` 내 자료에서 | (학생 자료가 있을 때만) 학생이 쓴 보고서·노트를 인용한다 |
| `box fix` 바로잡기 | (학생 자료가 있을 때만) 학생 자료가 강의와 어긋난 곳 |
| `box ans` 답 | (학생 자료가 있을 때만) 학생 자료에 남긴 질문에 대한 답 |

학생 자료(개인 보고서, 필기)가 과목 폴더에 있으면 읽고, 그 설명을 인용해 맞는 곳은 다듬고 틀린 곳은 바로잡는다. 학생이 자기 말로 쓴 설명이 고쳐지는 것을 보는 것이 가장 기억에 남는다. 학생 자료가 없으면 이 세 상자는 쓰지 않는다. 학생 이름 같은 개인 정보는 가이드에 넣지 않는다.

## 3. 자가 점검

- 단원마다 2~6문항. 객관식 `<div class="q mcq" data-id data-answer>`과 서술형 `<div class="q" data-id>` + `.a`.
- 문제 작성 원칙(`question-rules.md` 1절)을 그대로 따른다: 혼자 풀린다, 강의 용어만, 정수 계산(슬라이드 예제 값은 그대로), 객관식 해설에 매력적인 오답이 왜 틀렸는지.
- **클리닉이 있으면 클리닉 문제를 옮기지 않는다.** 가이드의 점검은 "방금 읽은 것을 이해했나"를 보는 가벼운 확인이고, 문제 풀이는 클리닉이 맡는다. 같은 문제가 두 곳에 있으면 어느 쪽이 최신인지 헷갈린다(기계학습 과목에서 실제로 별도 문제 아티팩트를 지운 이유).
- `data-id`는 한번 정하면 바꾸지 않는다. 문제를 바꾸면 새 `data-id`를 준다(예전 "이해함" 표시가 남지 않게).

## 4. 실습

실습은 손으로 조작하면 이해가 느는 개념에만 넣는다. 만드는 데 시간이 많이 들고, 틀린 그림은 해롭다.

- **넣을 만한 것**: 값을 바꾸면 모양이 바뀌는 것(함수, 경계, 변환), 과정이 단계별로 진행되는 것(반복 알고리즘, 학습 과정), 직접 계산해 보는 계산기(강의 예제 값으로 확인).
- **넣지 않는 것**: 정의·분류·사실을 외우는 개념, 그림 한 장(SVG)이면 충분한 것.
- 구조: `<div class="lab"><span class="tag">직접 해보기</span><h4>제목</h4><p class="how">조작법</p> … <ul class="try">해 볼 것</ul></div>`. "해 볼 것" 목록이 실습의 핵심이다. 무엇을 바꾸면 무엇을 보게 되는지, 그것이 어떤 개념인지를 쓴다.
- 스크립트는 조각 끝에 인라인 `<script>`로, 실습마다 `(() => { … })()`로 감싼다. 공용 도구 `G`를 쓴다: `new G.Plot(canvas, view)`(좌표, 격자, 곡선, 화살표, 점, 글자, 포인터 좌표), `G.lab(draw)`(테마·창 크기·단원 전환 때 다시 그리기), `G.bindOut()`(슬라이더 값 표시 `data-for`), `G.rand(seed)`·`G.gauss`(재현 가능한 난수), `G.css("--c1")`(색), `G.fmt`.
- 색은 CSS 변수(`--c1`~`--c5`, `--fg`, `--muted`, `--grid`, `--axis`)만 쓴다. 어두운 화면에서도 맞는다.
- id는 모든 단원을 통틀어 하나여야 한다(한 페이지에 모두 들어간다). 단원 키나 개념 이름을 앞에 붙인다.
- 실습이 강의 예제 값을 재현하면 그 값으로 시작하게 하고, 결과가 강의와 같은지 확인한다.

## 5. 피할 것

- 강의를 문단째 옮겨 적기(그것은 요약본의 일)
- 요약.md에 없는 정의·정리를 가이드에서 처음 꺼내기
- 비유를 강의 용어처럼 쓰기
- 클리닉 문제 은행을 자가 점검으로 복사하기
- 장식용 실습(조작해도 개념이 드러나지 않는 것)

새 과목에서 사용자 피드백으로 일반 원칙이 나오면 이 목록에 더한다. 과목 고유의 예시는 쓰지 않고 원칙으로 적는다.
